# v0.8.0 unobtrusive compaction plan

Status: accepted on 2026-11-03, not yet executed. The maintainer took every
decision as proposed except U7, where the synchronous writer was chosen over the
tail writer, and set the provider thresholds as proposed. Nothing in this plan
authorizes a release, a provider run, a change to the resident fingerprint or
the evaluation pin, or a change to the checkpoint format: WP5's budget is still
approved before its first request. The plan covers the 0.8.0 milestone in the
[roadmap](roadmap.md#planned-minor-releases), whose entry is the binding
authority for scope and acceptance: can compaction stop interrupting the task
without weakening its checks?

The maintainer asked a second question while this plan was being written:
whether 0.8.0 should instead have the core take over compaction on Pi, DSH and
OpenCode, with the adapters written by Codex cloud. The answer is in
[What 0.8.0 can reach](#what-080-can-reach) and
[Host takeover](#host-takeover-what-limits-it).

## What 0.8.0 can reach

On Pi, a boundary that prepared segments cover can cost a local merge, the
commit checks and a disk readback instead of a writer call: seconds, where the
writer took 108 to 186 s at the reasoning level the maintainer uses every day.
Every part of that path except the segments and their merge already ships
behind the preview's preparation and work-note switches, so the release is
mostly composition.

It cannot make every boundary cheap. The first boundary after a restart, a
branch switch, a tripped breaker or an ambiguous correction still runs the
synchronous writer, and that writer's failure still blocks. The release
therefore reports two pauses: over covered boundaries, and over all boundaries
with each fallback's cause.

It should not make takeover on DSH or OpenCode a gate. The limit on those hosts
is not the amount of adapter code, which a coding agent can write, but extension
points and contract decisions that adapter code cannot supply. DSH is the
exception worth starting now, on a parallel track: its public extension points
already allow a Gated adapter, and the one decision it needed, U11, about where
its checkpoint is stored, has been taken.

Three facts follow from these rows.

**The time goes to writing, not reading.** After the cache fix, Pi's writer read
95 to 97% of its input from the cache and still paused 108 to 186 s at `max`,
in step with the 2,000 to 15,000 reasoning tokens Luna spent per call. Cheaper
writer calls help; moving them out of the boundary helps more.

**Lower effort loses carried facts, not current ones.** At `off` Luna cited 131
of 136 current facts against 134 at `medium`, but carried 69 of 110 earlier
facts against 94. With segments, earlier facts are carried by a deterministic
merge rather than rewritten by a model, so the loss `off` showed falls on work
no model does any more. This is the strongest reason to measure segments at a
low effort, as the roadmap's third confirmed change asks.

**Hosts that pause briefly write little.** Codex wrote summaries of 0.8 to 1.3 KB
and kept up to 20,000 tokens of user messages verbatim (64,000 on its remote
path); DSH's summaries were 1,109 to 1,357 tokens without reasoning. Slice's
notes run to 7 to 11 KB with a citation on every fact. A pause measured on
another host is therefore not a target for Slice; the bench compares Slice
against its own synchronous control first.

The brief that prompted this plan needs six corrections:

- Oh My Pi's grace band is not a wait. Requests go ahead while speculation runs;
  at the cap the run is aborted and a blocking compaction starts from scratch.
- Registering `session_before_compact` turns off all of Oh My Pi's speculation,
  not only its native path ("Speculation is skipped while an extension registers
  `session_before_compact`", `docs/compaction.md:530`). This is why preparation
  stays in Slice's core.
- Mastra's seeded test never fails a call, restarts or switches a branch. Slice's
  version must add all three.
- Pi Context Plus uses one percentage of the window, not per-model thresholds.
- DSH ASC does not show that DSH's persistence gap is closed; it accepts weaker
  semantics.
- OpenCode V2 has been released: `@opencode/cli` 2.0.0 on 2026-09-11, with 2.2.5
  the latest. [host-adapters.md](host-adapters.md) and the
  [adapter design](dsh-opencode-adapter-design.md) still treat it as
  development code.

What this means for the maintainer's question:

- Code is not the constraint. Codex cloud can write every adapter in the table.
  It cannot add a hook a host does not offer, and it should not settle the
  contract questions.
- **DSH:** start now as track T1, under U11. The roadmap already lets
  DSH follow at any time after 0.7.0. It neither needs 0.8.0 nor holds it up, and
  it gains segments as soon as it can write checkpoints, because segments live
  in the core.
- **OpenCode:** aim at V2 rather than emulating Gated on 1.x. File the two
  upstream requests of T2 and keep `slice-opencode` retrieval-only on 1.x.
- **Codex:** belongs to 0.9.0's capability review. The evidence above already
  places it at Checked through its hooks.

## Decisions

Decided by the maintainer on 2026-11-03. U7 chose the synchronous writer over
the tail writer; every other decision was taken as proposed. U12 is a
conditional decision: its work starts only if WP5's evidence meets the stated
condition.

| ID | Decision | Consequence |
| --- | --- | --- |
| U1 | 0.8.0 answers the roadmap's question on Pi. DSH writing runs as track T1, with its own acceptance and version. No OpenCode or Codex adapter work gates the release | The release ships when Pi's evidence is in, whatever the other hosts' state |
| U2 | A segment is a preparation candidate over a closed range. Beyond what a candidate records today, it names the range's first and last record IDs, its base (the previous checkpoint's ID and hash) and the hash of the validated segments before it. It is usable only as the next link of a contiguous chain from the base's `coveredThrough`, and the boundary merges the longest valid prefix of that chain | A failed or invalid link ends the chain there; later links wait or are discarded, never merged out of order |
| U3 | The core chooses each range. A range closes only at a settled turn in which every tool call has its result; one that cannot close defers without advancing. Starting values: a range of `clamp(floor(0.15 × trigger), 8,192, 32,000)` tokens of new history; the first segment of an interval starts when the context passes half the trigger and covers everything uncovered so far, so a session that never nears compaction pays nothing | Values are measured in WP5. At a 150,000 trigger the range is 22,500 tokens and the first segment starts at 75,000 |
| U4 | The segment writer keeps the session writer's transport: the session's request through the range's last record, then a closing instruction that names the range, renders the current merged note and limits sources to the range. `supersedes` may name earlier records. Only the suffix changes, so the session's cache serves it. A range-only transport (merged note plus the range's originals, uncached) is measured as the alternative for providers whose cache serves only continuations it has seen | Rule K6 holds: the transport is the adapter's |
| U5 | Segments are measured at `off`, `low` and the session's level, and the default is set from that measurement, as the roadmap's third confirmed change says. The synchronous writer keeps mirroring the session | Expected to cut both segment cost and segment latency; the merge carries earlier facts |
| U6 | The merge generalizes `mergeWorkNotes`. A segment may add instructions sourced in its range. A carried instruction is retired only by a ruling: an instruction that supersedes its source and cites a user message in the segment's range. A superseded source that supports more carried instructions than rulings replace, or more earlier items in all than the segment gives in their place, sends the boundary to the synchronous writer. The newest nonempty plan and the newest listed gaps win. No verbatim user-message section is rendered: that belongs to arm B's notes, which do not restate instructions | Ambiguity is never resolved by guessing. Amended in WP3 at the maintainer's decision: the rule first sent every superseded instruction to the writer, which made every boundary after a changed ruling fall back |
| U7 | The synchronous writer. The merge commits through the prefix path with its existing conditions, plus Oh My Pi's check that the incoming request still fits. When segments do not cover enough, the synchronous writer runs as now, from the originals and the previous checkpoint, and the segments are discarded for that boundary. The alternative proposed with it, a tail writer that would write only the uncovered remainder on top of the merged note, is not built | Fallback pauses stay as long as today's synchronous pause, so the all-boundary P95 depends on how rarely segments fall short; WP0 and WP5 report each fallback's cause |
| U8 | No request is held below the request guard. At the trigger, compaction may wait for a segment in flight whose range would make coverage sufficient, for at most a starting value of 15 s, then falls back. The segment in flight is not aborted at the fallback: its calls stay journaled, and a result that is still valid serves the next boundary | Differs from Oh My Pi, which aborts at the cap |
| U9 | One segment in flight per session. At most eight segment calls per interval, repairs included. A spending cap per interval from journal usage, with unknown usage counted against it. A breaker after three consecutive failures, keyed by failure class (refusal, tool call, exhausted output), until the next commit. Cancellation happens the moment classification would say `invalid` (session, epoch, branch or writer changed), not lazily | Any limit sends the next boundary to the synchronous path and never blocks work |
| U10 | Segments stay in memory, as the roadmap says. The report gives the share of boundaries that follow a restart | Persistence is a later scope decision, taken only on that evidence |
| U11 | Where a DSH checkpoint is stored, for T1: (a) inside the native `compaction/summary` event, as a tagged block beside the rendered note or in `rawOutput`; or (b) wait for DSH to declare a backend field. Taken: (a) for a preview that states it relies on a field DSH owns, with a reopen test on every listed DSH version, and (b) requested upstream at the same time. The event is log-only, so the model reads only the rendered note in the replacement message that follows it. [host-adapters.md](host-adapters.md#dsh-writing) and the adapter design record the changed rule | T1 can start; the adapter moves to a declared field once DSH ships one |
| U12 | Stable fact identities, needed before any writer consolidates merged segments. The core assigns identities and the writer only refers to them; they are stored in checkpoint details beside an unchanged note schema and rendering, so earlier versions still reopen the checkpoint (to be verified against v0.7.5's reader). Taken up only if WP5 shows schema or budget bounds among the leading causes of synchronous fallback | Without it, merges that outgrow the bounds fall back to the synchronous writer, as the roadmap allows |
| U13 | Segments ship off by default. Turning them on by default is decided after WP5 meets the acceptance criterion | The same course as arm A |

## Work packages

### WP0 Measurement first

The bench gains `--arm segments`, run beside the synchronous control on the
same day with the same model, effort and settings. It reports the pause of
every boundary, covered and fallback alike, the coverage at the trigger, each
fallback's cause, segment calls by outcome (merged, discarded, failed,
cancelled), writer input and output tokens, cache reads and writes, and request
overhead. A loopback mode with simulated writer latency and context growth
reproduces arm A's synthetic result, about 1.1 s down to 0.1 s, and extends it
to chains. No provider is called.

Progress on 2026-11-03: arm A's checkpoints record `preparationFallback`, and the
loopback A/B runner runs chains (`--cycles`), sends input without waiting
(`--pace immediate`) and reports pause percentiles, the pause without a
foreground writer and each fallback's cause. The baseline is in
[validation.md](validation.md#080-wp0-the-loopback-ab-baseline-over-chains-2026-11-03-utc).
The `segments` arm and coverage at the trigger join when WP3 adds the switch and
its status fields; the provider bench's `--arm segments` follows for WP5.

### WP1 The segment contract in the core

Types and pure functions beside `preparation-candidate.ts`: freezing a segment's
input, classifying a chain, merging a chain onto its base. The specification
gains the coverage invariant in one sentence: after every boundary, each
original after the base is covered by a committed checkpoint, by a merged
segment, or is still in context verbatim, and never by none of them.
Conformance vectors cover chain validity and every merge bail-out.

Progress on 2026-11-03: `segments.ts` freezes, finalizes, classifies and merges
chains, `mergeWorkNotes` became `mergeNotes` with its refusal reasons, and the
specification has the chain and the coverage invariant, with focused tests in
`test/segments.test.ts`. `conformance/segments.json` pins the contract in 24
vectors under `0.8-conformance.1`, covering every chain stop and merge refusal.
WP1 is done.

### WP2 Range selection and the scheduler

A core function chooses the next range under U3. The Pi adapter calls it at a
settled turn and dispatches through the existing writer transport and journal,
under the limits and breaker of U9. Journal records name the phase `segment`.

Progress on 2026-11-03: `nextSegmentRange` chooses each range under U3, and
the session writer writes a segment when `writeMemory` is given its range: the
session's request, closed by an instruction that names the range, carries the
current merged note and limits citations to the range. A fixed writer writes no
segment, as U4 keeps the session writer's transport. The Pi adapter's
`PreviewSegments` runs one segment at a time from `agent_settled`, keeps the
chain in memory and cancels the run in flight when the session, branch or
writer changes, or when a checkpoint commits. Its calls are journaled with the
purpose `segment`. Three choices fill what U9 left open, all starting values
for WP5:

- The spending cap is the trigger's worth of uncached tokens per interval
  (input, cache writes and output; cache reads are U4's intended path), and a
  call with unknown usage spends all of it.
- The breaker's classes are refusal, tool call and exhausted output, plus
  error for everything else, a missed deadline included. A different class
  restarts the count.
- A note that cites outside its range is refused after the call and counts as
  a refusal; WP5 reports how often, before the writer's scope pruning learns
  ranges.

The settings switch arrives with WP3, so turning segments on never pays for
links that nothing merges yet.

### WP3 Assembly at the boundary

Merge, prefix commit, readback. `/compaction-status` shows how many segments are
ready, how far they cover and the coverage share; the doctor and the notices
follow the 0.5.2 voice. A fallback records its cause in
`details.preparation.segmentsFallback`, as arm B records `notesFallback`.

Progress on 2026-11-03: `previewSegments.enabled` switches segments on, off by
default (U13). At the boundary the chain's valid prefix is merged with
`mergeChain`, validated against the records it covers and committed through the
prefix path under the notes path's bound: the result must leave less than half
the threshold in context, which serves as U7's check that the next request
still fits. A chain that reaches the branch's last entry covers everything and
commits as a complete candidate does, since the prefix path would keep the
covered last turn verbatim. U8's wait applies only when the chain alone does
not commit for want of coverage (`in-flight`, `cut` or `fit`) and the segment
in flight extends it. Readback is the existing commit path. `/compaction-status`
shows `segments` with `ready`, `coveredThrough` and `coverage`; the doctor
reports segments that are off, inactive for a fixed writer, or paused by the
breaker. Segment instructions now require one `state` fact, which the note
schema demands.

The A/B runner's `segments` arm measured the result in
[validation.md](validation.md#080-wp3-segments-on-the-loopback-ab-2026-11-03-utc).
Over two cycles segments pause like A. Over six, every boundary after the
second fell back on `instruction-superseded`: the script moves the port each
cycle, and U6 sent any segment that supersedes a carried instruction's source
to the writer, even when it replaces exactly that instruction.

The maintainer decided to amend U6. An instruction now merges under the rule
facts follow, with one more condition: only a ruling retires it, an
instruction in its place that cites a user message in the segment's range. A
fact, a work note or an instruction that cites only assistant records still
sends the boundary to the writer, so a model cannot withdraw a user's ruling
by writing a segment. The segment instruction asks for a replacement in the
same section, naming every source previousNote cites for what it replaces.
Two vectors pin the change in `segments.json`, now 26, and the
[rerun](validation.md#080-u6-amended-the-loopback-ab-rerun-2026-11-03-utc)
measures it.

### WP4 A seeded lifecycle fuzz

Structured like Mastra's, with seeded weighted operations, and extended with
what Mastra's lacks: writer failures and timeouts, restarts, branch and model
switches, and a manual `/compact` in the middle of a chain. Scripted segment
notes cite exactly their range. Invariants: coverage, chain contiguity, a
`coveredThrough` that never moves back, no fact duplicated from the same source
without a reason, and a journal entry for every call.

Progress on 2026-11-03: `test/context-memory-preview-fuzz.test.ts` runs the
fuzz against the Pi preview. The harness stands in for Pi: it emits the
extension's events in Pi's order, commits what the compaction hook returns,
reports a cancelled compaction as Pi does and runs the compaction that
`ctx.compact()` asks for. Each seed runs 48 weighted operations: short and long
turns, answered tool calls, aborted turns, a writer refusal, tool call,
exhausted output, error or hang, a provider fault that repeats until the
breaker opens, `/compact` with and without focus, restarts, `/tree` to before
or after a checkpoint, and model switches. A blocked user retries the prompt
before running `/compact`. The scripted writer cites exactly the range it is
given and keeps one instruction per standing ruling, so changed rulings
exercise the amended U6.

Beyond the plan's five invariants it checks two the project already promises:
a failed compaction blocks the next request until a checkpoint commits, and an
explicit `/compact` always recovers at the end. The second found two faults in
`makeRoom` that 0.7.x already had. It started a compaction at most once per
checkpoint interval on any branch, so `/tree` back before a checkpoint returned
to an interval it had already served; and it checked only after a turn, so
`/tree` to a point near the limit left the next turn to push the context past
the room the session writer needs. In both cases every `/compact` then failed
with `CONTEXT_WRITER_CAPACITY`. `/tree` now clears the latch and checks the
room at once. Six deliberate faults, one per invariant, each fail seeds. CI
runs 40 seeds; the release gate's 200 and a run of 1,000 pass, as
[validation.md](validation.md#080-wp4-the-lifecycle-fuzz-2026-11-03-utc)
records. WP4 is done.

### WP5 Provider acceptance

Fixture P5 on the 200k and 272k routes, with Luna at `max` (the daily level) and
`medium`, and with DeepSeek V4.1 Flash, segments beside the synchronous control.
Probes cover current, carried and superseded values, among them a value
corrected between rounds. The maintainer approves requests, minutes and cost
before the first request.

### WP6 Fact identities, conditional on U12

Identities, their storage and the writer's references to them, then background
consolidation under the full commit checks, keeping every source ID,
`supersedes` ID and quotation, as the roadmap's 2026-10-17 decision requires.

### Track T1: DSH writing, parallel and not a gate

Under U11, in three stages: a manual `compactNow` with the gate, readback and
reopen; then automatic triggers; then segments, once WP3 has landed. The
[DSH writing preview](dsh-writing.md) is the design, written on 2026-11-03 for
Codex cloud to implement. It settles the question this plan left open: the
checkpoint goes into `rawOutput`, which DSH's chat view does not show, rather
than into a tagged block in `summary`, which it renders. It also lists what the implementation
must not add. Acceptance runs on the newest DSH release the acceptance matrix
pins.

Progress on 2026-11-03: stage 1 is built
([#115](https://github.com/youxi-huang/slice/pull/115)). With the profile
opt-in, `/compact` writes the checkpoint into DSH's log, reads it back and gates
the next request, and acceptance on rc.5 drives two chained compactions, a forced
failure, recovery, a CLI reopen and `context_history` through the loopback
provider. Stage 2, the automatic trigger, is next.

### Track T2: upstream requests, no code

- OpenCode: a typed admission refusal for plugins, and plugin access to records
  older than the latest compaction.
- Codex: a PreCompact output that supplies the summary, and an option for hooks
  to fail closed.
- DSH: a declared backend field on `compaction/summary`, carried by format
  migrations, and a pre-step rejection that keeps the claimed input queued
  rather than discarding it.

## Release gates

Offline:

- `node scripts/context-memory-ops.mjs verify` and both acceptance checks pass.
- Strict stock-Pi acceptance passes on every listed Pi with segments off and on,
  and the 50 ms request-overhead target holds with segments on.
- The conformance vectors, segment vectors included, pass; the lifecycle fuzz
  runs at least 200 seeds without a violation.
- Checkpoints committed from segments reopen in v0.7.5, since the format does
  not change, and v0.4.x and v0.5.x checkpoints reopen in 0.8.0.

On a provider, within the maintainer's budget:

- Pause P95 over all boundaries falls against the synchronous control on the
  same day. Thresholds, set by the maintainer on 2026-11-03: P95 of at most
  5 s over covered boundaries, and over all boundaries at most half the
  control's.
- Recovery accuracy holds: no fewer correct answers on P5's probes than the
  control, superseded values included, and no new wrong answers. Abstentions are
  reported.
- Validated coverage at the trigger, the cost of discarded and failed
  preparation, total writer tokens and cache reads and writes are reported
  beside the control.

## Deferred and out of scope

- A second history store, persisted segments unless U10's evidence changes the
  decision, and any vector index.
- A substitute writer on failure: blocking stays the default. The opt-in
  reduction fallback, the roadmap's fourth confirmed change, waits for 0.6.0's
  provider benches M3 and M4, which have not run.
- Unchecked rolling summaries in any form, Mastra's reflector and Oh My Pi's
  update prompt included.
- Provider-native compaction payloads such as Codex's encrypted item, which the
  roadmap places after 1.0.
- Emulating Gated on OpenCode 1.x, and adapters for OpenCode V2 and Codex, which
  belong to 0.9.0's review.
- The resident runtime, its fingerprint and the evaluation pin.
- Hard compaction as a gate. The roadmap evaluates it in 0.8.0 without making it
  one.
